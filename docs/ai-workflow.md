# AI 协作工作流记录

> 记录本项目里 AI 参与的部分、人做的判断、以及出问题后是怎么查出来的。
> 目的是可复现：同样的流程换个项目仍然能用。

## 1. 分工

| 角色 | 承担的工作 |
|---|---|
| 人 | 产品决策（做哪个场景、删哪个场景）、视觉验收（"割裂""方块感""不像湖"这类判断）、真机连接与人工确认 |
| AI | 工程初始化、模块结构、Kotlin/GLSL 编码、单元测试、Gradle 配置、部署脚本、文档、按视觉反馈迭代 |

**关键结论**：视觉好不好看，AI 判断不了；但"为什么难看"可以用像素度量定位，这一层 AI 比人快。

## 2. 代表性 Prompt 记录

### 2.1 工程初始化（一次性长指令）

计划书第 7 节给出的硬性约束，直接影响后续所有产出：

- 不用 Flutter / RN / WebView 替代原生
- 不用静态图或循环视频冒充实时 GPU 渲染
- 不用随机数或硬编码假数据冒充性能指标
- 不把规则解析器冒充 LLM，不把未接入的 MNN 冒充已完成
- 结果无法验证时必须明确报告，不伪造
- 每阶段更新开发日志并列出改动文件、构建命令、测试结果

这几条在后续每一次迭代里都被复用：凡是"看起来完成了"的说法，都要能指向具体的构建输出或真机截图。

### 2.2 视觉迭代（短反馈，多轮）

实际使用的反馈都是极短的，没有技术细节：

| 用户原话 | AI 的处理 |
|---|---|
| "好丑啊，又是这种非常割裂感" | 量出地平线处亮度跳变 0.213，改为让湖面顶端取天空地平线色 + 雾化倒影 |
| "我感觉极光有些方块感不是很细腻" | 定位到 `sin(dot)` 哈希 + smoothstep 插值在 26× 频率下的网格，换成 Hoskins 哈希 + quintic 插值 + 多频正弦 |
| "湖面的倒影有些不真实，而且湖面是否过于平静了" | 改成真正的镜像几何（把水面点反算到天空高度再采样），叠加波纹扰动 |
| "起伏太过规整。统一了。感觉随机点会更好" | 三频正弦 + 噪声歪相位 + 噪声调制振幅 |
| "湖面感觉也不像湖面，第一反应我还以为渲染错了" | 像素度量发现湖面缺"与岸上景物对应的形状"，补雪山倒影 |
| "湖面跟山的层级好像渲染错了，湖面好像在山上" | 量出反射高度是山本体的 1.26 倍（`MIRROR` 常量与 depth 归一化尺度不一致） |
| "流光长在山上" | 定位到极光帘幕下缘正好切在水平线上，加高度裁剪让其在脊线之前淡出 |

**规律**：用户只给感受，AI 负责把感受翻译成可测量的量（亮度比、跳变、条带周期、频率），
再翻译成代码参数。这条链路一旦断掉（比如直接猜"把颜色调暗一点"），就会反复返工。

### 2.3 要求回退时

"恢复到上 2 个版本"——项目没有 git 仓库，AI 按本轮实际部署过的版本次数回退，
并明确指出回退到的那一版正是用户此前抱怨过的状态，同时给出更深的回退选项。
**没有 git 是真实短板**，见第 5 节。

## 3. AI 引入的错误，以及怎么发现的

| 问题 | 发现方式 | 修复 |
|---|---|---|
| `SnowSystem.reset()` 没清 `vertexCount` | 单元测试 `resetClearsState` 失败（`expected 0 but was 700`） | 补 `vertexCount = 0`，测试改名并明确断言 |
| 删 `param_meteor` 字符串导致编译失败 | `:app:assembleDebug` 报 `Unresolved reference` | 补回字符串资源 |
| 安装新 APK 后壁纸画面不变 | 截图与预期不符 | 壁纸进程未重启，需 `am force-stop` 后重新设置 |
| 场景被重置回 Forest Night | 真机截图场景不对 | DataStore 默认值生效，改为在场景库手动选定 |
| 极光方块 | 用户反馈 + 放大截图 | 换哈希与插值方式 |
| 湖面被误判为"比天空亮 1.31" | **度量本身错了** | 桌面截图含应用图标污染中位数；改用 livepicker 预览页全屏截图 |

**教训**：度量工具本身要先被验证。上面那次误判导致 AI 朝着"把湖调暗"的错误方向做了两轮。

## 4. 验证方式

按可靠性从高到低：

1. **真机实测**：`docs/deploy.py` 构建 → 安装 → 设置壁纸 → 截图；`docs/shot_preview.py` 拿无 UI 遮挡的全屏图
2. **像素度量**：`docs/diag_lake.py`（逐行中位数、行/列梯度、亮度比）
3. **单元测试**：106 个用例，覆盖配置校验、序列化、规则解析、粒子生命周期与时间步进
4. **构建与 Lint**：`assembleDebug` / `testDebugUnitTest` / `lintDebug`
5. **人工看**：最终由人决定"能不能接受"

**从未使用**：让 AI 自行声称"看起来不错"。视觉结论一律来自截图或像素数据。

## 5. 已知短板

- **没有 git**。所有迭代靠人工记忆与文件内容回退，第 10 轮的改动就是因为无法精确回滚而整体重写。
  已通过"每次改动前先读文件、改动后立即部署截图"部分缓解，但这不能替代版本控制。
- **没有 CI**。`.github/workflows/android.yml` 已存在，但只能在推送到 GitHub 后生效，本地无法预演。
- **视觉判断无法自动化**。像素度量能查出"亮度比异常""条带周期异常"，但查不出"不好看"。
  最终仍是人看截图拍板，这也是本类项目最耗时的一环。

## 6. 可复用的做法

1. 把用户的主观反馈翻译成**可测指标**，再动手改代码。
2. 每次改动后**必须**部署 + 截图，不能只跑通编译就宣称完成。
3. 单测写得"能抓住实现错误"而不是"能跑通"——`reset()` 那个 bug 就是这样被抓住的。
4. 度量工具本身要先用已知正确的样本校验一次。
5. 无法验证的事情，明确写"未验证"，不写"应该没问题"。
